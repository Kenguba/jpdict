## 架构、代码质量与体积硬约束

以下规则属于工程级硬约束，适用于新增功能、Bug 修复、重构、性能优化、测试、构建与发布。

### 总体开发原则

- **轻量优先**：优先使用平台已有能力和项目现有能力，避免为很小的问题引入大依赖、大框架或重复实现。
- **高内聚、低耦合**：同一功能的状态、规则和行为尽量聚合在同一 feature / 模块内；跨模块通过清晰接口交互，避免互相直接操作内部实现。
- **多复用**：重复 UI、业务规则、网络/存储逻辑、格式化与平台能力应抽成可复用组件、工具或服务，禁止复制粘贴式扩展。
- **可扩展**：新增功能优先通过扩展点、接口、组合和配置完成，避免不断向单一超大类追加分支。
- **最小范围修改与根因分析**：先确认行为基线，定位问题实际发生位置及根因，检查调用方和共享状态读写；必须在原位置直接修改生效的属性、条件、函数或配置。禁止在文件末尾追加覆盖代码，禁止新增重复 selector、函数、状态或事件监听来绕开原逻辑；禁止猜测式修复和无关重构。
- **兼容优先**：已有可用行为、公开入口、数据格式和用户习惯不得因为无关重构被破坏。
- **回归与回退**：对比修改前后的 diff、体积及适用的函数、事件、状态和持久化结构；验证目标及关联旧行为，无法实测须说明。发生回归优先撤销错误修改，不叠加补丁。
- **依赖克制**：新增第三方依赖前必须确认项目现有能力无法低成本解决；能用小依赖解决时不得引入重型框架。
- **避免过度设计**：遵循 KISS、YAGNI、DRY、SRP；先改原实现，再按需提取重复逻辑或最小抽象。设计模式仅用于解决现有耦合、重复或扩展问题，不为套模式增加类和层级。

### 架构设计要求

工程架构思路需要与 **Flutter 主流可维护架构思想**保持一致，但当前工程仍是原生 Android Java，**不得为了形式上的“符合 Flutter”而额外引入 Flutter Runtime 或无必要框架**。

默认采用以下等价原则：

- 优先 **feature-first** 组织：按功能聚合代码，而不是把所有页面、所有服务、所有工具无限堆进少数大文件。
- 复杂功能按需拆分为 `presentation / domain / data / platform` 等边界；简单功能不得为了分层而机械增加文件。
- UI / 展示层只负责展示、交互和轻量状态协调，不承载可复用的核心业务规则。
- 业务规则尽量独立于具体 Activity、Service、网络库、数据库和系统 API。
- 数据访问优先通过稳定边界封装；需要时使用 Repository / Adapter / Facade，避免上层直接依赖底层实现细节。
- 状态来源要清晰，避免同一状态在多个对象中重复保存、互相同步。
- 平台能力、网络、AI、存储、OCR 等外部能力需要可替换、可测试，避免业务代码和具体 SDK 强绑定。
- 优先组合而不是继承；优先小接口而不是“大而全”接口。
- 新增抽象必须能实际减少重复、降低耦合或提供明确扩展点，否则不新增抽象层。

- **工业级设计原则与设计模式**：遵循 SOLID、KISS、YAGNI、DRY、高内聚低耦合、关注点分离和单一状态源。优先沿用现有架构，在原位置进行最小必要修改。仅当现有实现确有重复、耦合、职责混乱或扩展困难时，才按需采用成熟、经过工业实践验证的设计模式或架构方法，不限于特定模式。禁止为了套用设计模式而增加无意义的类、函数、状态、依赖或抽象层。任何设计模式都必须服从最小修改、行为兼容及回归验证要求。

### 文件与类的控制

- 禁止继续制造职责混杂的超大 Activity、Service、Manager 或 Utils。
- 一个类出现多个独立变化原因时，应优先拆分职责。
- 公共工具必须有明确边界，禁止形成“万能 Utils”。
- 新功能优先复用已有组件；若需要新增公共组件，应保证命名、职责和 API 足够稳定。
- 重构优先小步进行，保持每一步可构建、可验证、可回退。

### 代码体积上限

最终工程的 **Git 跟踪的项目自有代码、资源与配置总量不得超过 35 MB**。

统一按以下规则理解：

- 上限按 `35 × 1024 × 1024 bytes` 计算。
- 统计 Git 跟踪的工程自有文件。
- 不统计 `.git`、Gradle/Maven 缓存、Android SDK、构建缓存、临时文件和下载的外部依赖。
- 不允许通过把大量代码或资源改成压缩包、Base64、生成文件等方式规避限制。
- 接近上限前必须先做去重、资源压缩、依赖裁剪和结构优化，而不是直接放宽限制。

### APK 体积上限

**任何最终面向用户发布的单个 APK 都不得超过 30 MiB。**

统一按以下规则理解：

- 上限按 `30 × 1024 × 1024 bytes` 计算。
- `arm64-v8a`、`armeabi-v7a`、`arm` 等所有正式发布 APK 都必须分别满足限制。
- `universal` 只有在自身也满足 30 MiB 上限时才能作为正式发布产物。
- 如果 `universal` 因包含多个 ABI 超过 30 MiB，必须停止发布该 universal APK，优先使用 ABI Split / 分架构 APK。
- 新依赖、新资源、新模型加入前必须评估对 APK 体积的影响。
- 发布前必须检查实际 APK 文件大小；超过上限视为发布阻断问题。

## 版本规则

对外版本号固定格式：

```text
YY.MM.DD-NNNNNX
```

示例：

```text
26.10.07-00001A
26.10.07-00002D
26.10.07-00003B
26.10.07-00004T
26.10.07-00005C
26.10.07-00006R
26.10.07-00007P
26.10.07-00008H
```

阶段字母固定为：

| 字母 | 阶段 | 含义 |
| --- | --- | --- |
| `A` | Alpha | 原型阶段，可无构建产物 |
| `D` | Development | 开发调试 |
| `B` | Build | 成功构建 |
| `T` | Test | 测试 |
| `C` | Candidate | 发布候选 |
| `R` | Release | 正式发行构建 |
| `P` | Production | 正式生产版本 |
| `H` | Hotfix | 生产环境紧急修复 |

### 流水号规则

`NNNNN` 为 5 位十进制流水号。

同一天：

- 所有阶段共用同一条流水号序列。
- 阶段字母变化时，流水号**不归零**。
- 每产生一个新版本，`NNNNN` 继续递增。

例如：

```text
26.10.07-00001A
26.10.07-00002D
26.10.07-00003B
26.10.07-00004T
```

换一天：

- 使用新的当天日期。
- 当天流水号重新从 `00001` 开始。

例如：

```text
26.10.07-00008H
26.10.08-00001D
```

### Android / iOS 内部构建号

对外版本号与平台内部构建号分离。

- Android `versionCode` 必须保持**纯数字、永久递增**。
- iOS build number 必须保持**纯数字、永久递增**。
- 不允许直接把带日期、连字符或阶段字母的 `YY.MM.DD-NNNNNX` 硬塞进 Android `versionCode` 或 iOS build number。
- 平台内部构建号跨日期、跨阶段都不能回退或重复。

`version.properties` 记录已分配的本地版本。GitHub Actions 将此记录与远端标签、已发布版本及上传中断留下的草稿版本合并计算下一版本；Android 构建号同时考虑当前 Workflow 流水号，避免 Workflow 更名或重试造成回退。新的本地版本分配后也必须更新该记录。

## APK 命名规则

APK 文件名固定格式：

```text
名字-YY.MM.DD-NNNNNX-ABI.apk
```

示例：

```text
名字-26.10.07-00004T-arm64-v8a.apk
```

其中版本部分必须严格使用本 README 定义的 `YY.MM.DD-NNNNNX` 规则。

当前 Android 常规发布使用的架构 / 变体后缀包括：

- `arm64-v8a`
- `armeabi-v7a`
- `arm`

`universal` 仅在最终 APK 本身不超过 30 MiB 时允许发布。

因此构建产物命名应遵循同一规则，例如：

```text
名字-26.10.07-00004T-arm64-v8a.apk
名字-26.10.07-00004T-armeabi-v7a.apk
名字-26.10.07-00004T-arm.apk
```

如果 universal APK 控制在 30 MiB 以内，则可使用：

```text
名字-26.10.07-00004T-universal.apk
```

## 当前实现

- 原生 Android Java
- OCR 内置拉丁字母、中文、日文和韩文模型；首次识别不需要 Google Play 服务或联网。目标 OriginOS 无 GMS 真机和逐语言识别率仍需按 [OCR 根因与验收方案](docs/2026-10-15-ocr-root-cause-and-test-plan.md) 实测，内置模型不代表准确率已经通过。
- 自研纯 Java MDX/MDD v1/v2 引擎，共用随机读取、块索引、原生 zlib 与独立 LZO1X 解压逻辑；未接入任何第三方 MDX/MDD 解析器。精确查词保留重复和空词条，支持跨块记录及 `@@@LINK`，重定向优先匹配目标的原始大小写，兼容大小写别名指向正文，真实循环与损坏文件明确报错。兼容 `Compact/Compat=Yes` 但 `StyleSheet` 为空的普通 HTML，以及 v2 `Encrypted=2` 的校验和派生索引混淆（独立 RIPEMD-128 实现，仅用于格式读取）；索引摘要允许按大小写及 `StripKey/Stripkey` 标记规范化，实际查询仍按原词头精确匹配。当前验证以项目原创生成样本及有限本地词库为主，不能据此宣称兼容全部商业词典；v3、密码保护（`Encrypted=1/3`）、v1 索引混淆、非空 `StyleSheet` 的 Compact 样式替换明确不支持。
- 对完整 v2 MDD 末尾追加的短 nginx HTTP 416 完整错误页作窄范围兼容：仅在 Record 声明/索引结束位置精确匹配不超过 512 bytes 的已确认模板时忽略该尾部，所有数据块解压、校验和、索引、长度和取消验证继续生效；未知尾部、截断和损坏依然失败，不改写原文件。
- 设置顶部“词库管理”卡片入口（独立保留“关于”按钮），已安装与词库下载两个标签；已安装页面提供搜索、双列导入/迁移入口与紧凑词库卡片，点击在列表内展开/收起详情，同一时间仅展开一本；书本图标按名称生成柔和颜色，白字对比度至少 4.5:1，优先取一个汉字，否则取首字母。详情操作依次为浏览词库、重命名、文件管理、查词展开和卸载；查词展开使用同一眼睛轮廓，关闭时蓝色描边与白底，开启时填蓝色并保留白色眼圈、按钮浅蓝底，不显示开/关角标；整块按钮可切换，辅助功能保留可勾选状态。查词展开默认关闭，数据库升级、替换安装和完整/轻量备份均保留设置。长按卡片/手柄排序时抬起缩放（无阴影）、显示空位、其他卡片平滑让位，松手吸附落位，取消返回原位；筛选时只重排可见词库所在的位置，不移动隐藏记录。所有列表隐藏滚动条；支持 SAF 多文件、递归目录、多 MDX 文件夹内选择词库并关联同名/编号 MDD 与配套 JS/CSS/字体、外部持久授权、流式内部导入、取消、稳定 ID、重命名、替换/重新关联、开关、拖动/无障碍按钮排序、删除内部副本及解除外部关联。内部文件在 `files/Dicts/<dictId>/<文件代次>/`，先验证再以数据库记录提交；中断时保留旧版本并清理未提交代次。原始外部文件不会因删除或迁移被删除。
- 悬浮查词和无悬浮权限的备用 Activity 共用 Repository 与原生分区控制器；展示顺序固定，加载前全部收起，保留各词库的查词展开意图，正文页面完成后再展开；首本和可见分区优先，同级后台任务按显示顺序执行，显式展开保留最新操作优先。后排默认展开词库每次延迟加载一本，不可见正文不创建 WebView。最多两个工作线程、96 个排队任务、两个解析器、三个活跃 WebView；收起保留 DOM、资源与测量高度，重开复用。共享正文使用引用计数的磁盘 HTML 文档，缓存最多 32 MiB / 64 项，大于缓存定额的词条仍正常显示而不驻留；旧 String API 保留 2 MiB / 64 项缓存，跨窗口和解析器淘汰复用，文件身份变化或安装更新时失效；私有安装代次以 URI/修改时间/大小快速命中，外部文件继续校验指纹，未知修改时间不缓存。冷解析与指纹 I/O 不持有解析器池全局锁，驻留私有解析器借用不重复打开文件或计算 SHA。关闭/切词取消旧任务并拒绝旧 View 更新，查询期间暂停联想；超过 1 MB 的字节数组读取串行以约束内存；大正文在后台流式解压到磁盘，显示层不构建整个词条的 String/byte[]。HTML 与词典资源继续通过 WebView 本地隔离 Origin 拦截，沿用既有 CSP、路径校验、本地 JS/JSON、entry://、sound:// 和 src/mdd 目录兼容规则；仅为 workClick.js 的欧路笔记只读接口和固定版本调试脚本提供窄范围联网适配，其余网络继续阻断。
- 词典块 LRU 每个解析器最多 4 MB；辅助索引保存实际词头范围和合计最多 2 MB 的 Bloom 过滤摘要，不依赖某一种词典排序规则；摘要只排除不可能匹配的块，命中后仍精确核对词头。导入逐块验证时就按最终 URI/指纹/修改时间保存索引，避免首次查询重复扫描；后续打开复用校验有效的索引。索引缓存最多 32 MB / 64 个文件；文件指纹与修改时间变化时失效。无法提供可靠修改时间的外部文件不复用持久索引。不再固定拒绝大词条、MDX 正文块或 512 KB HTML；100 MiB 大块正文通过磁盘支持的流式 raw/zlib/LZO 解码，并继续验证长度、校验和、重定向和取消。MDD 字节数组资源接口保留 16 MB 上限，外部资源流式读取 32 MB（字节数组接口仍限制 8 MB）、索引 4 MB；缓存定额用于约束驻留量，不作为正文显示限制。最多 512 本安装记录，全部资源清单合计限制 4 MB。
- 词库与 MDD 配套资源验证采用最多两线程、每批最多两文件，等待两个读者关闭后再提交或清理代次。词库操作由进程级协调器与前台 Service 维持，弹窗使用 20dp/16dp 留白、18sp 标题、14sp 正文；“后台加载”以 380ms bitmap mesh 漏斗动画缩成右下角可拖拽全局球，单击恢复，完成显示完成；新搜索、查词、OCR 页面打开后进度球重新置顶。加载通知保持低优先级，完成和失败使用独立结果频道，点击直接回管理页查看。页面退出或销毁不取消工作；无悬浮权限用通知回管理页，Android 13+ 首次词库操作请求通知权限。系统终止进程后任务不自动续传，原子安装和启动清理保证已提交版本不被破坏。

- OCR、Intent 与搜索查词小窗必须自己消费左右返回手势、系统返回和实体返回键，统一调用 `handleLookupBack()`，一次返回直接关闭整个小窗；编辑态和查询历史都不得拦截为“退出编辑”或“上一词”。收起键盘并移除 Mask 后，底层应用保持原页面；搜索入口可恢复原搜索查询。蓝色悬浮球始终位于查词浮层最上层。
- 对外查询 Deep Link 固定为 `jpdict://lookup?q=<URL编码后的查询内容>`（旧链接 `jp-native://lookup` 仍兼容接收）；由无界面的 `LookupLinkActivity` 接收后转发到 `FloatingService.ACTION_SHOW_LOOKUP_OVERLAY`，Deep Link 本身不得渲染或切换到查词 Activity 页面
- Deep Link 继续接受 `mode=fullscreen` 与 `mode=float`，两者在 Intent 入口都采用同一可拖动、可缩放小窗和全屏 Mask；不再因入口或 mode 改变卡片大小和交互。词典卡片仍是 `TYPE_APPLICATION_OVERLAY`；透明、无预览、无动画、空 taskAffinity 的 `LookupLinkActivity` 只承载 Mask 和系统返回，不渲染词典页面，并在小窗关闭时 finish。OCR 入口仍通过显式 Intent 将识别原文直接交给 Service，由 Service 复用该透明宿主；返回关闭后保持原桌面或应用，不恢复搜索层。
- OCR、Intent 与搜索的 WindowManager 根层覆盖整个显示区域并允许布局进入刘海区域。卡片外点击通过独立 Mask 点击层调用关闭方法；系统返回键、Android 13+ 返回回调和左右边缘返回手势统一调用 `handleLookupBack()`。
- 全屏黑色 Mask 使用约 42% 不透明度，由透明 `LookupLinkActivity` 的独立全屏 View 绘制，覆盖底部、状态栏和导航栏；系统栏透明且关闭系统额外 contrast scrim，关闭宿主后恢复调用方系统栏。`TYPE_APPLICATION_OVERLAY` 根层保留独立的卡片外点击层，宿主已绘制 Mask 且没有保留搜索页时此层不重复着色，避免双重变暗；保留搜索页时由 Overlay 遮罩覆盖搜索视图；没有宿主时由 Overlay 自己绘制 Mask。不能仅依赖悬浮窗口扩大范围或半透明 Root background 保证系统栏遮罩。
- OCR、Intent 与搜索小窗顶部词头支持编辑态：长按词头 700ms 才切换为输入框 + 蓝色“确认”并弹出键盘；轻点不修改，超过 touch slop 的移动取消长按并拖动窗口。编辑态返回也直接关闭整个小窗并收起键盘。OCR 触发期间蓝色悬浮球不得临时设为 INVISIBLE。
- OCR、Intent 与搜索小窗的系统返回由透明、无动画、可触摸的 `LookupLinkActivity` 在小窗生命周期内接收。Android 13+ 通过 Activity 的 `OnBackInvokedDispatcher`、旧版本通过 `onBackPressed()` 把返回发送给 `FloatingService.ACTION_LOOKUP_BACK`；小窗关闭后 Service 通知宿主 finish，保持调用方页面不变。
- 普通浏览/全屏 Mask 状态下已接入透明宿主的 OCR、Intent 与搜索查词 Overlay 保持 `FLAG_NOT_FOCUSABLE`，由透明 Back 宿主接收系统返回；长按词头编辑、词典网页表单输入或 Key 配置期间临时去掉该标记获取 IME，退出编辑后恢复。点击网页普通 input/textarea/contenteditable 时确认命中元素，再让窗口取得焦点并建立原生输入连接；不改变网页字段类型，不读取字段值、不增加 Android Bridge。只读和普通释义不启动编辑，隐藏/切词/关闭清理编辑；旧页面和旧触摸异步结果不得改变新编辑状态。
- OCR 成功后的查词请求与 Intent、搜索选词共用透明 Mask / Back 宿主，不渲染无宿主的 `mode=float` 结果。普通浏览由宿主接收返回，Overlay 保持 `FLAG_NOT_FOCUSABLE`；词头、Key 或词典网页输入编辑时临时聚焦并注册 `PRIORITY_OVERLAY` 回调，一次返回同时关闭键盘、查词和 Mask，底层应用不得收到该次返回。
- 搜索浮层的 Android 13+ 返回回调使用 `PRIORITY_OVERLAY`，与宿主共用 `handleSearchBack()` 的分层收起规则。抽屉横滑避开系统返回边缘；取消手势只恢复抽屉位置，不能关闭窗口或把同一手势传给底层应用。旧版输入框通过 `onKeyPreIme()` 消费返回。输入区在首次取得 IME 高度前采用初始预留，随后以系统提供的最终 Insets 高度更新并按方向持久化；键盘收起时保留预留空间，显隐不反复移动输入框。Android 11+ 在首轮测量前应用已有预留，onApplyWindowInsets 仅记录待确认高度，当前动画结束或连续高度稳定后才写缓存并平滑校准；重复分发的中间帧和过期动画结束回调均不写入记录。旧系统在可见区域稳定后平滑校准，不能长期使用固定估计值。只在 IME 退场结束或明确收起时释放编辑焦点，避免进场动画中途失焦。
- 搜索页在密度、字号和方向变化后重新布局，保留查询草稿与私密状态；查词返回搜索后的宿主重建不能再次打开旧结果。横屏输入禁止输入法全屏提取，空间不足时收起顶部和推荐项并缩紧输入区；收起键盘后恢复布局。
- 搜索的私密态不写本机查询历史，也不读取或写入共享 AI 缓存；退出整个搜索或用户离开搜索任务时清除私密草稿；宿主明确发起的设置/第三方查词往返保留原会话，返回恢复，不能把草稿写入恢复 Intent。支持的输入法收到无个性化学习标志。AI 请求仍由 Groq 处理，不承诺第三方模型训练政策。界面不冒充 Grok 官方模型或会员；摄像头、图库、文件、技能、连接器、Image 和语音当前明确标为未接入。
- 搜索选词、查词返回搜索共用同一透明返回宿主。搜索输入框未编辑时 Overlay 保持 `FLAG_NOT_FOCUSABLE`，由宿主接收返回；编辑时临时聚焦搜索 Overlay 并注册返回回调。用户离开搜索任务时必须移除搜索、查词和 Mask，不得在后台恢复搜索；宿主明确发起的设置或第三方查词通过当前会话保护返回路径，第三方在前台时原搜索保持隐藏，仅宿主返回并取得焦点后恢复。
- vivo/OriginOS 的透明 Back 宿主不得设置 `FLAG_NOT_TOUCHABLE`，两种 mode 都保持可触摸、可聚焦，并在 `onPostResume()` 注册高优先级返回回调；上方 WindowManager Overlay 继续接收卡片和卡片外点击。
- 编辑态临时聚焦 Overlay 时，Android 13+ 在编辑期间注册 `PRIORITY_OVERLAY` 的 `OnBackInvokedCallback`，返回时关闭整个小窗；旧版本通过输入框 `onKeyPreIme()` 处理键盘之前的实体返回。恢复 `FLAG_NOT_FOCUSABLE` 时立即注销回调。
- 蓝色 `あ` 悬浮球本体禁止为了 Z 顺序执行 `removeView/addView`；查询过程中本体持续挂载，结果层上方使用同步代理窗口保持视觉与触控连续，避免“先消失再出现”的闪烁。代理挂载成功期间本体透明且不接收触摸，始终只显示一个图标；代理移除后恢复用户设定的透明度。键盘显隐不得自动改变浮球的用户保存坐标或代理窗口位置；浮球可与输入器重叠，由用户自行拖动。首次轻点悬浮球打开搜索自动聚焦输入框并弹出键盘；查词返回或设置页返回不强制再次弹键盘。输入区下方快捷入口与键盘边缘之间保留 8dp 间距；键盘预留沿用已缓存的当前渲染高度，动画中间值及重复 onApply 不写缓存；最终稳定高度才持久化，差异以 200ms 平滑校准，显隐后保留校准值。打字换行导致的输入卡片高度以 160ms 平滑变化，候选刷新不覆盖输入。
- 常规和句子 OCR 返回尽量完整的原始识别文本，不提前截取首词或长度，不擅自改写原文。用户明确选择英语单词模式时仅运行 Latin 模型并清洗为西方字母单词，去除中日韩文字和数字；选择日语模式时仅运行 Japanese 模型。模型脚本筛选属于识别意图，Groq 仍自行判断实际语种。
- OCR 的 Latin / Chinese / Japanese / Korean `TextRecognizer` 必须跟随 `ScreenCaptureService` 生命周期复用，禁止每次框选识别都重新创建并立即销毁；Service 退出时统一释放，仍在执行的识别完成后再安全关闭
- Groq 接收原始 OCR 文本作为用户消息，独立判断输入属于中文、日文、韩文、英文、混合文本或不确定语种；按实际语种解释，不得预设为日语或强制翻译成日语
- 简短汉字、模糊词语及语言重叠情形允许报告不确定性，不能假装能准确区别中文和日文

## Android CPU 架构 / ABI 说明

这里的 v7、v8 指的是 Android 设备的 CPU 指令集架构（ABI），不是 Android 系统版本。

| ABI | 简称 | 位数 | 主要设备 / 用途 |
| --- | --- | --- | --- |
| `armeabi-v7a` | v7 | 32 位 | 老 Android 手机、旧平板 |
| `arm64-v8a` | v8 | 64 位 | 现在绝大多数 Android 手机 |
| `x86` | x86 | 32 位 | 老模拟器、少量旧设备 |
| `x86_64` | x86_64 | 64 位 | 模拟器、部分 Chromebook / 特殊设备 |

## APK 下载建议

正式发布 APK 必须同时满足上面的版本化命名规则和 **单 APK ≤ 30 MiB** 的体积硬限制。

| 架构 / 变体 | 包含架构 | 建议 |
| --- | --- | --- |
| `arm64-v8a` | `arm64-v8a` | 推荐给现在绝大多数 Android 手机，体积最小 |
| `armeabi-v7a` | `armeabi-v7a` | 老旧 32 位 ARM 手机 / 平板 |
| `arm` | `arm64-v8a + armeabi-v7a` | 手机通用集合版，兼容新旧 ARM 手机 |
| `universal` | `arm64-v8a + armeabi-v7a + x86 + x86_64` | 仅在最终文件 ≤ 30 MiB 时允许发布 |

普通用户建议：

- 新款 Android 手机：下载 `arm64-v8a`
- 不确定新旧 ARM 架构：下载 `arm`
- 老旧 32 位设备：下载 `armeabi-v7a`
- 模拟器 / Chromebook / 特殊设备：优先使用对应 ABI 构建；不得为了兼容而发布超过 30 MiB 的 universal APK。

> `arm64-v8a` 和 `armeabi-v7a` 是当前手机端最重要的两种 ARM ABI。x86 / x86_64 如需支持，应继续采用分架构产物或控制在 30 MiB 上限内。

## 固定 Release 签名

正式 APK 使用固定 Release 证书。公开证书保存在：

`signing/jpdict-release-cert.pem`

证书 SHA-256：

`CB:8B:97:98:9B:FE:78:94:E7:96:84:2C:E5:B2:E3:E3:B2:AA:B4:8A:A7:F0:F7:A9:7C:1E:CE:04:AC:18:42:52`

私钥 / JKS 不提交到仓库。GitHub Actions 读取以下 Repository Secrets：

- `ANDROID_KEYSTORE_BASE64`
- `ANDROID_KEYSTORE_PASSWORD`
- `ANDROID_KEY_ALIAS`
- `ANDROID_KEY_PASSWORD`

如果这 4 个 Secrets 尚未配置，Workflow 只生成临时 Debug Artifact，不发布正式 Release。Secrets 配好后，重新运行 Workflow 即可生成固定签名的正式 APK。

> 注意：GitHub Actions 的具体实现必须服从本 README 的版本与 APK 命名规则。Android `versionCode` 仍需使用独立的纯数字永久递增序列。

## 本地构建

为控制 APK 体积，默认只构建当前可发布的 3 个变体；universal 不作为默认发布产物。

Debug：

```bash
gradle --no-daemon \
  :app:assembleArmDebug \
  :app:assembleArm64Debug \
  :app:assembleArmv7Debug
```

正式 Release 构建需要先提供固定签名环境变量，然后运行：

```bash
gradle --no-daemon \
  :app:assembleArmRelease \
  :app:assembleArm64Release \
  :app:assembleArmv7Release
```

GitHub Actions 会自动重命名 APK、验证签名、计算 SHA-256、上传 Artifact，并创建 GitHub Release。发布步骤最多重试三次，显式发布草稿；必须通过按标签读取正式 Release 的接口，核对当前提交、正式发布状态及三个 APK/校验文件均上传完整后才算成功，不能仅依据 CLI 返回的草稿链接。所有产物名称和版本号必须遵守本 README 的规则。

推送到 `main` 时使用 `R` 正式发行阶段；手动运行 Workflow 时仍可选择其他阶段。
