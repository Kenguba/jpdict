# OCR 失灵与误识别：根因、修复和对抗性验收

## 根因

1. **模型不可用（确定的设备兼容问题）**：原依赖是 Play 服务提供的动态 OCR 模型。代码发出安装请求后没有等安装完成，也没有把进度或失败状态传给界面；无 Play 服务、首次离线或模型尚未下载时，随后的识别自然失败。仓库原有记录也明确写着缺模型要联网，目标 vivo/OriginOS 是否有 GMS 未知。
2. **截图暂时不可读被误报成授权失效（确定的恢复问题）**：`ScreenCaptureFrames` 会缓存一次 `ImageReader` 异常，后来收到正常帧时旧异常仍然保留。`captureOnce` 又把读帧异常直接等同于 MediaProjection 授权失效，导致 OCR 反复要求重新开授权。
3. **准确率没有被证明（测量结论，不是推测成修复）**：现有的 27 个合成字体探针中，旧模型英文原始整串匹配为 6/9、精读为 7/9；日文和中文各 9 个探针没有可靠识别。样本太少且不是目标设备截图，不能支持“识别准确”或“新包准确率提高”的结论。小字、低对比度、缩放、混合脚本和错误语言模式都需要按真实屏幕单独测量。

## 本次解决办法

- 将拉丁字母、中文、日文、韩文 OCR 改为 APK 内置模型，删掉 Play 服务动态模型安装请求和 Manifest 下载元数据。模型随应用安装；首次使用识别不再依赖 GMS 或联网。
- 首次帧等待继续有限重试；短暂 `ImageReader` 异常允许新帧恢复并清空旧错误。重试耗尽只提示屏幕帧暂不可用，不再伪装成授权失效。真实 `captureAlive()` 检查仍负责识别真正失效的共享授权。
- 离线模型增加包体：三 ABI Debug APK 实测 arm64 18,731,777 bytes、armv7 14,449,175 bytes、arm 双 ABI 25,524,850 bytes。CI 的 APK 上限同步改为 30 MiB；仍按每个发布 APK 分别检查。最终 Release 体积和签名必须以 Actions 的实际产物为准。
- 使用临时本地测试证书完成三 ABI Release 构建（该证书不适用于安装升级或发布）：arm64 17,721,426 bytes、armv7 13,438,819 bytes、arm 双 ABI 24,514,600 bytes；三个 APK 均包含四种脚本对应的模型资源，且小于 30 MiB。Actions 另有逐 APK 模型资源守卫，避免后续依赖改动悄悄移除离线模型。

## 对抗性审查

- **无 GMS 仍无法证明真机可运行**：SDK 模型文件存在于 APK 只是必要条件。必须在无 Play 商店、无 GMS 的干净安装上启动全部语言识别，并在断网时首次识别。模拟器有 GMS，不能代替这项验收。
- **模型内置只解决模型可用性，不会自动修正错字**：本次没有宣称 CER/WER 改善。当前小型合成样本反而暴露出日中识别不稳；真实目标机语料通过前，不应宣传准确率已修复。
- **包体与升级风险**：离线模型带来约 14–25 MiB 的安装包。每个 ABI 都要做 Release 构建、检查压缩后真实大小、证书与版本；arm 通用 ARM 包应是最大值。已安装旧版还要验证固定签名升级路径。
- **帧异常可能是持续故障**：有限重试后界面必须结束当前操作并允许下一次操作；不可无限重试、卡住预览状态、重复申请录屏授权或泄漏 `Image`。
- **真实授权撤销需保持正确**：短暂帧故障应恢复；用户在系统设置撤销共享授权后必须停止读取并正常要求重新授权，不能靠缓存帧继续识别。
- **语言分派与结果选择仍有风险**：混合模式并行运行多种脚本模型，区域重叠结果依赖几何与启发式质量排序；这可能造成重复候选或选错词。应报告逐语言指标并保留原图、模式和结果，不能只看“返回非空”。
- **混合模式的性能风险**：它会对同一截图并行调用四个识别器。低内存或低端设备上要重点测峰值内存、卡顿和被系统杀进程；若出现压力，应优先做脚本分派/顺序识别基准，不可先隐藏语言或吞掉失败。
- **模型更新风险**：内置模型不会被 Play 服务单独更新；模型升级跟随应用版本，需要在每个正式 Release 包中更新并重新跑精度语料。

## 建议验收 / 测试方案

### A. 模型可用性和发布包

1. vivo/OriginOS 真机无 GMS、无 Play 商店、开启飞行模式，清除应用数据后分别做拉丁字母、中文、日文、韩文首次识别。模型不得出现缺失/下载错误；恢复网络和 GMS 状态不应改变识别入口。
2. 分别安装 arm64、armv7 和 arm APK，验证应用启动和四种语言调用。记录设备、Android/OriginOS 版本、ABI、安装包 SHA-256、是否有 GMS、网络状态和错误码。
3. 固定证书验证覆盖新安装及上一正式版原地升级；确认设置、词库文件及查询数据保留。Release APK 必须小于 30 MiB，包名、版本、签名证书指纹和 SHA256SUMS 全部匹配。

### B. 截图和恢复

1. 同一静态页面连续识别 100 次；快速滚动期间连续请求；横竖屏旋转、亮屏/息屏、应用切前后台后分别重复 20 次。应无重新授权误报、无旧会话结果覆盖新结果、无预览卡死。
2. 让首帧延迟、短暂 `ImageReader` 读异常、Projection 真正撤销分别发生。前两者应有限重试后恢复或清晰报“帧暂不可用”；只有最后一项重新申请授权。
3. 重复开启/停止共享 50 轮，观察 `Image`/Bitmap 回收、内存曲线和服务状态；失败、取消、超时后立刻再试必须成功进入新会话。

### C. 分语言识别质量

1. 从目标设备真实界面制作带人工转写的固定语料：每种语言至少 100 张裁剪，覆盖正常印刷字、不同字体/字号、低对比度、深浅色主题、缩放、行间距、混合日文假名/汉字/拉丁字母、标点和干扰图标。另记录竖排文字、振假名、小于 12sp、运动模糊等困难样本，单独报数。
2. 每张图分别跑用户选择的语言和混合模式，保存原始 OCR、区域边界、置信信息、处理耗时和截图。报告归一化 CER/WER、整句完全匹配率、目标词命中率、错误非空率，并按上述难度分桶；与旧版在可运行的参考设备上同图对比。
3. 发布门槛建议：模型冷启动/调用成功率 100%；干净语料字符错误率相对旧版不得回退；低对比度、小字和混合脚本逐桶不得只用总平均掩盖退化。真实语料数据和门槛未达成前，不发布“准确率提升”结论。

### D. 对抗样本

- 空屏、只有图标、长段正文、双栏、混合脚本、重复词、标点边缘、屏幕边界裁切、错误语言选择、极小选区、低对比度/反色、渐变背景、缩放后文字、快速变化画面、连续撤销授权。
- 断网、GMS 缺失、低存储、旋转中请求、连续多次请求、取消后立即重试、识别完成前切换语言、旧截图回调晚到。
- 通过条件不仅是“不崩溃”：输出不得串会话；失败能恢复；不会把旧帧默认为新帧；不会将授权问题提示成模型下载问题；空间预算、签名、版本及校验和均通过。

**当前执行状态**：三 ABI Debug 与 Release 构建、三 ABI Lint、Release 临时测试签名检查、30 MiB 体积和 APK 内四种模型资产检查已完成；Lint 每变体 0 errors / 111 warnings。临时证书不能验证正式证书升级兼容。本轮未执行无 GMS 真机、目标语料精度、固定证书升级或真实 Release 签名验收；已有合成字体探针只记录旧动态模型的低样本结果。该文件是验收方案，不是 OCR 精度通过报告。
